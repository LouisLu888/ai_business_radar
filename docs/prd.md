# AI Business Radar：每日 AI 生意一手信息简报

版本 0.3 · 2026-10-08 · 完成两轮交叉评审，待产品 review

每天打开手机，用 5 分钟看到关注的人新分享了哪些经营经验：做什么生意、谁付钱、AI 用在哪一步、怎样获客、结果如何。每条内容都有中文要点和原文入口，能继续核查。

**第一版建议：从 5–10 人开始，每天更新一次，首页突出最多 5 条重点，其余相关内容完整保留。** 首先验证真实来源能否取得正文，再实现界面与自动采集。公开代码，阅读实例默认单人登录。

阅读顺序：先看用户流程和范围，再看页面草图、摘要规则、验收标准。开发顺序与费用见 [实施计划](plan.md)，工程细节见 [技术设计](rfc.md)。

[同类产品调研](landscape.md)显示，订阅、转写和自定义摘要已有成熟方案。自建的待验证价值是把人物身份、嘉宾访谈、经营数字口径和原文证据放进同一日更流程，减少每天查找和修正的时间；中文摘要或经营字段本身不构成独有优势。Cloudflare 托管仍为当前设计约束。

Follow Builders 已有按人物追踪并生成中英简报的思路。本项目借鉴这一组织方式，但名单由用户维护，并单独记录经营成果依据；不能把通用 AI 从业者名单当成已取得商业结果的人选。

## 1. 每天完成一次从发现到阅读的选择

用户提交人物名单及已知链接。系统建立人物档案，确认本人频道、播客、网站和 newsletter，并登记常见访谈节目。

每天早上，用户先看到新增数量和更新状态，再按经营类别浏览中文卡片。对感兴趣的内容打开原文，或者收藏留待周末阅读。历史内容能按人物、日期和类别回看。

用户要得到的答案有三个：今天多了什么；它能帮助理解哪种生意；原作者实际说了什么。首页优先呈现经营实践，允许当天没有重点推荐。

## 2. 一手来源、成果证据与相关性分别判断

**一手来源**包括本人发布的经验，以及本人作为嘉宾参与的原始访谈。其他人转述其故事、剪辑搬运、标题提及姓名，先进入待核实列表；确认原始出处后再收录。

**成果证据**保留经营结果的原始说法。收入、利润、月收入、累计收入、客户数各自记录；未说明币种或时间周期就标注未说明。本人自述和附有可检查材料分别显示，附链接也不自动代表独立审计。粉丝数、融资额不能代替付费客户或经营收入。

**逐条相关性**依据内容是否讲到真实产品、客户、获客、定价、交付、成本或经营结果，以及 AI 在其中的具体作用。名单中的人分享生活、泛新闻或无实操的工具发布时，仍可在来源记录里查到，但不进入默认经营简报。付费推广和 affiliate 内容标记商业推广；推广不自动等于没有信息价值。

白名单本人来源中的新条目，不能仅因标题没有 AI、播放量低或未达到热门阈值而提前排除。低成本元数据只用于处理排序；需要正文才能判定的条目等待获取正文。预算不足时标待处理，避免将其伪装成不相关。

用户提供的名单是初始白名单，系统保留选入理由和证据缺口，帮助用户判断可信程度。单个故事只能说明这个案例，不能推出某种副业的普遍成功率。

## 3. 第一版覆盖固定来源和有边界的访谈发现

| 来源 | 第一版行为 | 明确边界 |
| --- | --- | --- |
| 本人 YouTube | 每日检查频道上传列表，获取新视频字幕 | 无字幕或获取失败时保留链接，显示待补全文 |
| Podcast | 读取公开 RSS，优先节目逐字稿；缺稿时在预算内转写公开音频 | Spotify/Apple 页面用于定位节目；没有公开 feed 的独家节目逐项确认 |
| 网站与 newsletter | RSS/Atom 优先，获取公开文章正文；无 feed 时配置固定文章列表页 | 登录、付费墙及只发邮箱的 newsletter 列为待接入 |
| 第三方 YouTube 访谈 | 每日按姓名及别名做有上限的检索，核实本人是否参与 | 搜索排序、索引延迟及同名会影响覆盖，不能保证全网无遗漏 |
| 第三方 Podcast 访谈 | 每日扫描已登记节目，匹配嘉宾姓名并核实 | 新节目通过手动贴链接补录；全网播客搜索留到下一版 |

首页展示已接入来源数量和抓取失败数量；人物页逐项说明支持方式。所有用户提供的来源都必须有接入状态，不能静默丢弃。

每个来源分别显示能否发现新条目、取得简介、取得正文、取得真实时间位置，以及是否需要付费转写。界面用自然语言呈现，例如“能检查更新，字幕待验证”，不能只显示一个笼统的已支持 Podcast。

首轮试运行建议上限为 10 人、30 个固定来源；扩容基于真实更新量和成本。初次导入回补最近 14 天，每源最多 10 条；其余历史单独排队，避免一启动就转写全部旧节目。

首版包含分类筛选、历史日期、人物筛选、收藏、原链接、手动补录和重试。全文搜索、聊天问答、多用户、推荐关注新人、邮件推送、自动订阅邮箱和社交平台采集放到后续。

## 4. 手机端用三个入口组织阅读

底部入口为 **简报 / 收藏 / 人物**。简报提供今天、近七天与历史日期；点击卡片进入详情。人物页同时承担来源管理，避免额外建设后台系统。

以下全部内容与数字都是界面示意，并非采集结果：

```text
AI 生意简报                 10 月 08 日
07:00 已更新 · 新收录 8 条 · 1 个来源失败

[今天] [近七天] [选择日期]
[全部] [产品/SaaS] [服务] [内容] [其他]
[人物筛选]                 [仅看完整摘要]

今日重点  3
┌────────────────────────────────┐
│ Example Builder · 嘉宾访谈      │
│ 如何把重复交付变成付费自动化服务 │
│ 产品：… 客户：… AI 的作用：…     │
│ • 一条具体经营做法              │
│ • 一条获客或交付经验            │
│ • 作者报告的结果与限制          │
│ 收入：本人自述 · 基于完整字幕    │
│ [查看详情] [打开原文] [收藏]     │
└────────────────────────────────┘
其他相关内容  5
待补全文  2             查看获取状态

          简报    收藏    人物
```

**内容详情**展示中文标题、原始标题、作者/嘉宾/主持人、原发布时间、首次收录时间、来源类型、摘要依据和原链接。重点回答做什么、卖给谁、AI 如何参与、如何收费与获客、结果和限制。关键数字可展开查看短原文及时间戳或段落位置。

**人物页**展示追踪理由、成果证据、本人来源与访谈节目、最近成功检查时间、失败原因及启停/重试入口。添加人物时输入姓名、已知链接与可选说明；同名或频道归属不确定时由用户确认。

人物详情包含来源内容列表，可筛选全部、待核实和已排除。待核实项支持确认人物、拒绝和补充原始链接；已排除项显示理由并允许恢复。这样能纠正同名识别和相关性误判。

**手机交互**以 390px 宽为基准，兼容 360px；正文至少 16px，触控区至少 44px，单列卡片、筛选条换行。原文新页打开，返回保留列表位置；颜色以外同时使用文字标识状态。首版响应式网页即可，不额外开发原生 App 或离线同步。

## 5. 分类围绕生意，摘要围绕证据

每条内容只有一个主类：产品/SaaS、服务/咨询与自动化交付、内容/教育与数字商品、其他经营。类别描述商业模式；辅助标签描述经营环节：需求验证、获客、定价、交付、运营、成本，以及具体 AI 用法。工具名只是标签，避免页面变成工具资讯流。

列表每条给 3 个要点，共约 120–180 个中文字；详情约 300–600 字，根据原文信息量伸缩。没有提到的项目写未提及，避免为了填满模板而推断。

每个摘要应保留以下信息：

1. **内容价值**：一句具体说明，例如介绍首批客户来自哪个渠道。
2. **经营事实**：卖什么、谁付费、AI 的作用、获得的结果，以及适用条件。
3. **证据位置**：经营数字与关键主张绑定原文片段、段落或真实字幕时间；没有时间信息就只链接原文。
4. **信息缺口**：作者未披露的成本、团队规模或周期。读者应能区分作者事实与系统概括。

阅读依据分四种：完整文章、完整字幕/转写、部分正文、仅标题/简介。完整材料进入正式摘要；部分材料明确写明范围并进入待补全文；只有元数据时只展示中文标题和简介预告。自动转写额外标识机器转写，数字或说话人不确定时保留不确定性。

完整度分成两项：取得材料对原作的覆盖，以及已取得材料是否全部处理。前者保留提供方声明、可观察缺口和人工抽检依据；后者可由分块记录核验。提供方成功返回正文，不自动等同于读完整篇。只有来源覆盖有依据且无已知缺口、所有取得材料均已处理时，才能进入正式摘要，并注明依据，例如“据提供方完整逐字稿生成”。这不是系统独立保证原作一字不漏。

来源范围未知时显示“已处理全部取得材料，来源范围未确认”，归入待补全文；有已知缺口时标明缺失范围。没有可观察信号的中间缺失可能只能由人工抽检发现，发现后降级并重新处理，不承诺自动识别所有缺失。

排序采用可解释规则：与 AI 经营直接相关、有具体经营过程、有结果出处、较新且未重复。重点区最多 5 条，达不到标准就减少数量；相关内容区不因未入选重点而丢失。无需预测收入潜力或给人物打虚假的精确可信分。

重点区默认同一人物最多两条，避免更新频率高的人占满页面；其余仍在完整列表中。每张重点卡片给出一条具体入选理由，方便用户判断推荐是否有用。

同一访谈的 YouTube、音频版及原作者文章可归为一个内容组，卡片保留多个原链接。明确的同集标识或互链才能自动合并；标题相似但无法确认时保留两条，允许手工合并或撤销。长访谈中的某一句不能被归因给错误的嘉宾。

## 6. 每日更新同时说明完整程度

默认按 `America/Los_Angeles` 时区，每天 06:00 开始检查，目标 07:00 前出现简报。夏令时变化不改变本地阅读时间；时间和时区均可配置。

“今天”按首次收录到当日简报的时间归档，另行展示原发布时间。旧内容今天才发现时标注补收录；当天采集后新发的内容通常在下次日更出现。成功生成的内容立即可读，迟到摘要更新原卡片，不制造第二条新增。

首页明确区分四种结果：全部检查完成且没有更新、已有新内容、部分来源失败、尚未运行。摘要缺失也计入覆盖状态。两个连续日更失败时，在来源页突出显示；超过 26 小时未成功检查时显示已过期，不能继续显示今天已更新。

重试针对失败项目，不重跑全部成功内容。优先处理本人固定来源，再处理已确认的访谈；低置信第三方候选只用剩余额度，默认每天最多处理 5 条。预算用尽后继续收集链接和元数据，把需要付费处理的项目标为待处理，并显示暂停原因和预计恢复时间；额度恢复后继续原条目。首版通过网站状态展示异常，不向外发送通知。

## 7. 用真实样本和七天试运行判断是否成功

上线前冻结一组用户名单中至少 5 人、20 条人工确认相关的一手内容，覆盖文章、YouTube、自有播客及第三方访谈，至少一条无现成逐字稿但有公开音频。失败样本不得替换。另用独立负例测试同名、仅被提及、转述、无可用正文和截断等情形，负例不混入正文取得率的分母。

| 验收项 | 首版通过标准 |
| --- | --- |
| 来源覆盖 | 所有输入来源都显示支持状态；已启用来源每天留下检查记录 |
| 采集及时性 | 连续 7 天所有启用来源均有尝试记录；至少 6 天在本地 07:00 前完成至少 90% 来源的元数据检查，其余明确失败或处理中；正文完成率另计 |
| 正文取得 | 固定 20 条中至少 16 条取得满足正式摘要条件的正文；失败及范围未确认样本 100% 显示相应状态 |
| 一手与相关性 | 检查这 20 条实际生成的全部 N 条正式摘要，N 至少 16；至少 ceil(0.9×N) 条正确呈现相关的一手经营内容 |
| 摘要忠实 | 全部 N 条中关键经营数字与人物归因零编造、零收入/利润口径混淆 |
| 可追溯 | 每条有原链接；数字与关键主张有段落、片段或真实时间位置 |
| 去重恢复 | 同来源重跑不新增重复；多平台同集可合并且原链接不丢失 |
| 手机阅读 | 真机完成筛选、看详情、跳原文、返回、收藏和跨设备查看收藏 |
| 实际价值 | 用户七天里至少三天找到一条愿意深入读的内容；低产出来源可删减 |

80% 是启动阶段的产品门槛，不是对任意平台的可得性承诺。若正文覆盖不达标，先保留原组结果，再调整获取方式并对原组重测；若确需改变来源范围或接受更多仅链接条目，另记范围变更与新一轮样本，不能换掉失败条目后声称原验收通过。

本轮待评审的默认值与待提供信息集中在 [实施计划的评审项](plan.md#4-review-时只需要决定这些事)。
