# 两轮交叉评审：从功能对比到可验证的设计调整

日期：2026-10-08 · 主 agent 负责综合、改稿与最终核查；独立 agent 负责 GitHub 调研和反向审查。

原方案为 v0.1。用户要求先找同类产品，再讨论、修改两次；本文件保留每轮输入、异议与处理结果，详细事实依据集中在 [调研报告](landscape.md)。没有第三方项目运行结果，也没有把纸面 review 称作产品验收。

## 第一轮：先确认现成工具覆盖了什么

主 agent 调查六个网站，并提出将 Inoreader 作为现成方案对照、将 Briefings 作为 Cloudflare 技术参考。独立 agent 核查五个仓库的 README 和许可证，并审阅 Briefings 的正文与摘要源码。

| 讨论点 | 异议与交叉验证 | v0.2 的处理 |
| --- | --- | --- |
| 自建是否有必要 | 独立 agent 指出经营问题模板也能靠自定义 prompt 实现；主 agent 核对 Reader 和 Inoreader 文档后接受 | PRD 将差异写成需验证的端到端省时；计划增加有时限的同样本对照 |
| 是否整库 fork Briefings | 双方读到每批十篇与每篇约 2,000 字符的截断；与完整长访谈证据要求不同 | 保留模块参考，继续轻量 Worker 架构，不引入其队列/周报全套依赖 |
| 完整摘要如何判定 | 独立 agent 提醒成功返回 transcript 不等于全部已处理 | RFC 增加取得/处理长度、分块范围、截断和覆盖依据；测试加入假完整正文 |
| 是否模仿热度过滤 | 独立 agent 指出新闻项目的热度门槛会漏掉小众经营者 | PRD 明确播放量或标题缺少 AI 不构成排除理由 |
| 平台支持是否过于笼统 | 预建播客 feed 与任意音频转写的能力不同 | 人物页按来源展示发现、正文、时间位置和转写能力 |

主 agent 同时保留原有的覆盖列表与重点列表分离，并增加同一人物在重点区默认最多两条。已有能力明确作为保留项，避免把原方案中已有的原链接、预算和收藏重复算作新变化。

第一轮未采纳：情绪分数、趋势预测、知识图谱、向量去重、浏览器持久登录、多队列架构、全网播客索引和邮件分发。理由是它们增加首版维护，尚未证明能改善指定人物的经营信息阅读。
